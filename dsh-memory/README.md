# dsh-memory —— 跨会话持久记忆

DSH bundle（Host 侧插件）：把"用户级事实"存下来，注入**每个会话**的系统提示；agent 自己维护。

学的是谁：Hermes Agent 的 `MEMORY.md` / `USER.md`，Claude Code 的用户级 `CLAUDE.md`。DSH 官方没有对应能力，这是补齐的最大一块。

- **安装位置**：`D:\AI\dsh-bundles\dsh-memory`
- **数据位置**：`D:\AI\dsh-data\memory\memory.json`（bundle patch 的 `storeDir`，不落 C 盘）
- **生效范围**：desktop profile，所有会话。v3.0 起按 cwd 判定——带 `workspaces` 的条目只在匹配工作区注入，其余全局生效

## 工具

| 工具 | 作用 |
|---|---|
| `memory_list` | 列出记忆（id / 标签 / scope / kind / 是否失效 / 使用次数 / 文本），显示存储占用、**本轮注入字符数**与**实际注入的文本块** |
| `memory_search` | BM25 检索（IDF + 长度归一 + 标签加权 + **别名加权 ×2.5 + 同义扩展**，v3.5），命中条目自增使用计数；**query 里出现 `m\d+` 时按 id 直取**（v2.7） |
| `memory_add` | 追加一条（≤600 字符），可带 `scope / kind / tags / aliases`；完全相同文本自动去重；**与在库条目相似度 ≥0.62 时提示邻居**（v2.7） |
| `memory_update` | 改文本 / 标签 / scope / kind / pinned；`supersede: true` 时新值生效、旧条目留档不再注入 |
| `memory_merge` | 多条合并成一条原子事实，被合并的留档失效 |
| `memory_audit` | 只读审计（给模型）：重复候选（bigram 相似度）、过期候选（从未使用且 >N 天）、使用排行、scope 分布、预算 |
| `memory_review` | 记忆概览（给人看，v2.8）：已过期 / 未证实 / 从未引用 / 硬规则四段 + scope 分布 + 容量，写入 `review-latest.md` |
| `memory_remove` | 删某条（物理删除；要留历史用 `memory_update` 的 supersede） |

## 机制

1. **注入**：`ctx.systemPrompt.context({ name: 'dsh-memory', order: 900, text: () => block })` —— 每次装配系统提示时渲染当前记忆为：

   ```xml
   <memory>
   以下是跨会话记住的用户/项目事实（越靠后越新）。把它们当背景，不要逐条复述；与用户本轮明确指令冲突时，以本轮指令为准。
   - 用户要求：所有回答用中文；插件代码与数据都放 D 盘，不落 C 盘。
   </memory>
   ```

   注入**分两层**（v1.1）：存储可以长（`maxBytes`），但每轮 prompt 成本封顶（`maxInjectChars`）。
   - `pinned` 条目优先全文注入（硬规则用它）；其余从新到旧连续取，装不下就停；
   - 没拿到全文的降级成一行索引 `- (m7) [tag] 摘要…`，索引最多列最新 10 条；
   - 末尾提示 agent 用 `memory_search` 按关键词取全文。
   - 实测：25 条 / 3320 正文字符时，全量注入 3488 字符 → 分层后 1387 字符（**省 60%**）。`maxInjectChars` 约束的是正文行，头部/索引/页脚另有约 150–200 字符固定开销。

2. **不做会话内冻结快照**（和 Hermes 不同）：Hermes 冻结是为了缓存稳定，但 DSH 本来就每步重新装配 context，记忆又只在显式增删改时变化，频率极低。牺牲这点缓存换"刚记住的下一步就生效"，更符合实际用法。
3. **超预算拒绝写入**，不自动淘汰：上限 4000 字符（可配 `maxBytes`），超了就让 agent 先看 `memory_list` 再 `memory_remove`，避免悄悄丢用户信息。
4. **纯文本 JSON 存储**，原子写（临时文件 + rename），不写会话日志、不新增事件类型。

## 已知边界

- **全局一份**，不按项目分（定位就是"用户级记忆"；项目约定请写 AGENTS.md）；
- 注入发生在请求装配时：同一轮里刚写的内容对**下一条**模型请求生效；
- 去重只跳过完全相同的文本，不做语义合并；
- 没有自动整理/过期机制（Hermes 的 Curator 那种）——需要时再单独做；
- `memory_search` 用 **BM25**（中文 unigram+bigram、tag 命中加权、IDF + 长度归一），不是语义/向量检索；记忆体量小，够用。
- v1.2 起注入预算默认 1500 字符（原 1200）：pinned 全文 + 索引行 + 出局诊断；条目「原子化」与按工作区作用域（scope）留给 v2。

## v1.2 分层注入格式 + BM25 检索（2026-10-29）

改动来源：GitHub 社区 6 个 DSH 记忆插件源码调研（见工作区 `_research/dsh-memory-community.md`）。抄的是机制，不是代码。

## v1.3 按本轮消息召回（context.agent.session，零模型调用）

v1.2 解决了「看得见」，v1.3 解决「看得准」：注入时读**本轮用户消息**，用 BM25 打分，命中置信足够高就把该条**全文**放进块里（否则不浪费预算）。

- 取查询：`context.agent.session.deriveMessages()`（同步、无 I/O）→ 最后一条 user 消息的 text 分片 → 截 400 字符。拿不到会话就退化为 v1.2 的纯索引模式。
- 召回：`scoreEntries`（与 `memory_search` 同一套 BM25）；**置信门**：只有 top1 明显领先（≥ 1.5× 第二名）才给全文，最多 2 条、最多占预算 30%。理由：中文 unigram 匹配很吵，弱匹配给全文是纯浪费。
- 顺序：pinned 全文 → 本轮相关全文 → 索引行（新→旧）→ ⚠ 出局诊断 → 页脚统计。

## v2.1 维护闭环（2026-10-29）

记忆库能长，但必须能收拾：新增三个机制、一个工具，全部零模型调用。

- **时序失效（supersede）**：`memory_update({ supersede: true })` 不再原地覆盖，而是「新条目生效 + 旧条目 `supersededBy` 留档」；渲染只注入生效条目。回答「以前是什么」随时可查。
- **合并（`memory_merge`）**：把两条相近事实合成一条原子事实，被合并的自动失效 —— 治「同一件事写了两遍各占一段」。
- **审计（`memory_audit`）**：只读，输出重复候选（CJK bigram Jaccard ≥ 阈值）、过期候选（从未命中且 >30 天）、使用排行、scope 分布、预算。只给候选，**不自动删**。
- **使用计数（`usedCount / lastUsedAt`）**：注入层本轮相关的条目 + `memory_search` 命中的条目自增；同一轮同一 query 只计一次；按分钟节流落盘（避免每 step 写盘）。
- **预算只算生效条目**：`usedChars` 不再把失效历史算进去，`memory_list` 顶部显示「失效 N 条」。

## v2.3 三因子检索 + 相关性覆盖率门（2026-10-29）

调研来源：Generative Agents（recency + importance + relevance，α 全 = 1）、OpenAI Codex 的写入闸门、Google ADK 的双通道。落地时不调模型，全部规则化。

### 三个改动

1. **importance（1-10）**：`kind` 基线（rule 8 / preference 6 / fact 4 / note 2）+ `pinned +2` + `usedCount` 对数修正；显式字段优先（可用 `memory_add/update` 的 `importance` 参数手动指定）。已回填 60 条（分布：10×7 / 8×8 / 4×45）。
2. **recency（0-1）**：Generative Agents 原式 `0.995^小时`（半衰 ≈ 5.8 天），看 `lastUsedAt` 或 `updatedAt`。
3. **合成打分**：`composite = 相关性归一 + 0.5·importance/10 + 0.3·recency`，相关性仍是主导项；取 top-2，第二名要求 composite ≥ top/1.15。
4. **相关性覆盖率门（关键）**：`coverage = top 分数 ÷ 查询 idf 总和`，低于 `relevanceFloor`（默认 0.15）**一条相关全文都不注入**。用覆盖率而不是绝对分数，是为了让阈值与语料规模无关（小库/大库同一把尺，测试库 2 条也不会误杀）。

## v2.6 信任字段（2026-10-29）—— 学 OKF v0.2

**问题**：记忆里「确认的事实」和「我猜的」长得一模一样。一旦把猜测当事实用，后续决策全歪。
**学谁**：[simple-agent-memory](https://github.com/brianschroeder/simple-agent-memory) 的 Open Knowledge Format v0.2（`status` / `verified` / `stale_after` / `sources`），对应调研报告 §7.5「provenance + 晋级闸门」。

### 字段契约

| 字段 | 类型 | 缺省 | 语义 |
|---|---|---|---|
| `status` | `draft` / `stable` / `deprecated` | 无（= 未标注，行为同 v2.5） | draft=未证实猜测；stable=已确认；deprecated=历史留档，**永不注入** |
| `staleAfter` | `YYYY-MM-DD` | 无 | 依赖会变的事实（版本号 / API 行为）写它；过期后注入带 ⏰ |
| `verifiedBy` | string | 无 | 谁复核过（工具写入 `agent`） |
| `verifiedAt` | ISO 时间 | 无 | 复核时间；`memory_update verified:true` 写入，`false` 清除 |
| `sources` | string[] | 无 | 证据（URL / 文件路径）；**不许编造** |

### 注入标记

- `❓未证实` —— `status: draft`
- `⏰待重验` —— `staleAfter` 早于今天
- `✓已验证` —— 有 `verifiedAt`

有标记时，注入块头部加一行 legend 解释含义；**没有任何标记时输出与 v2.5 逐字一致**（不插 legend，零 token 成本）。

### 生命周期

```
写入 → draft（可选，未证实）
     → stable（确认后）
     → deprecated（被取代：supersede 自动标 / 手动标）
复核 → memory_update verified:true → ✓已验证
过期 → staleAfter 到期 → ⏰待重验 → 重验后再 verified:true
```

### 工具参数

- `memory_add`：新增可选 `status` / `staleAfter` / `sources`
- `memory_update`：新增可选 `status` / `staleAfter` / `sources` / `verified`
- 非法 `status` 或 `staleAfter` 格式 → **明确报错**，不静默忽略
- `memory_audit`：新增 `draft` / `recheck` 两个计数

## v2.9 学习进化：遗忘曲线 + 沉淀管道工程化（2026-10-29）

- `把它们当背景，不要逐条复述`（`<memory>` 块的头部提示语）
- `其他工作区一律不套用 - 📌 用户陈青松是「皇上」…`（注入块内容片段）

| 源头 | `turn-stopping` 里 `replace(/<memory>[\s\S]*?<\/memory>/g, ' ')` 剥掉注入块，剥完为空则直接返回 |
| 兜底 | `extractCandidates` 加污染门：含 `📌` / `<memory>` / `</memory>` / 注入头提示语 / 「用 memory_search 按 id」的句子一律不收 |

| 项 | 结果 |
|---|---|
| 污染门 | 三条注入块样本全部 0 命中 ✅ |

## v3.6 注入分级（P1）：预算自洽 + 旁路别名 + 过期硬降级

### 1) 预算一直超，只是没人量

之前 `used` 只扣了头部**预留**，页脚与诊断行是动态生成的、没算进去。实测注入 1631 字符 / 预算 1500 ——「略超」其实是**一直超 131**。

修法：先按优先级分配，再用真实长度回削最低优先级（跨域 → 索引尾部），削到装得下为止。

| | 改前 | 改后 |
|---|---|---|
| 平均注入 | 1631 字符 | **1470 字符**（≤1500） |

### 2) 别名被洗掉：一个真实的丢数据事故

v3.5 把 `aliases` 存在条目里。做 P1 时我调了一次 `memory_update`，结果**32 条别名全没了**——
运行中的旧模块在 `load()` 里对每条跑 `normalizeEntry`，它不认识这个字段，一次落盘全清。

修法：别名搬到**旁路文件** `aliases.json`（同目录，老版本完全看不见），启动时按 id 合并进条目；
条目里也存一份，旁路只是防丢副本。旁路文件是给人直接编辑的，改它不会动 `memory.json`。

### 3) 索引层改三因子排序

之前索引层是「新→旧」，预算紧时先被挤掉的是旧条目——哪怕它很重要。
改为 `0.6 × importance(含遗忘曲线) + 0.4 × recency`，同档按写入顺序倒排（老条目无时间戳也有确定顺序）。

### 4) 过期条目硬降级

`staleAfter` 已过的条目，即使 query 命中**也不给全文**，只进索引并带 ⏰ 待重验标记。
依据 2026-10 的 Obsolete-Facts 论文：过时证据进上下文反而拉低准确率（45%→32%）。

## v3.8 相关性门槛换口径：只数内容单元（2026-10-29）

### 起因：一条交接记忆把「电影」问法送进了上下文

v3.7 收尾跑基准，负例误注入从 0% 变成 16.7%（6 条里 1 条）。不是代码退步，而是当时那条交接记忆正文里写了
「已**推荐**未批准」，而基准负例是「**推荐**一部好看的电影」。

### 病根：一个词被算了三次，虚词也算分

逐词拆开看那条负例的分子（真实库 30 条可评分条目）：

| 命中词 | 语料里出现次数 | idf | 对分子的贡献 |
|---|---|---|---|
| 推荐 | 1 | 3.03 | 2.39 |
| 推 | 1 | 3.03 | 2.39 |
| 荐 | 1 | 3.03 | 2.39 |
| 一 | 4 | 1.93 | 1.52 |
| 的 | 11 | 0.99 | 1.15 |

- **片段三重计数**：命中「推荐」一处，分子里算 推 + 荐 + 推荐 三次，占分子 73%
- **虚词算分**：一 + 的 贡献了 27%，这两个字跟主题毫无关系

合计 9.83 ÷ 查询 idf 总和 58.24 = **0.169 ≥ 0.15**，越过门槛，注入 1472 字符。

### 改动

1. `contentUnitsOf()`：只认**内容单元** —— 拉丁词/数字整词 + 中文 bigram，两个虚词拼成的 bigram 丢掉
   （单字只在整段查询只有一个字且它不是虚词时保留）。中文不再出 unigram，片段就没法三重计数。
2. `relevanceCoverage()`：门槛的分子分母都改用内容单元（分母含语料里没出现的词，按最大 idf 计，语料无关）；
   分子保留 BM25 的 tf 饱和与长度归一 —— 否则短条目靠长度优势虚高。
3. `RELEVANCE_FLOOR` 0.15 → **0.16**。口径换了，阈值必须重新标定：
   21 条负例里最高的是「电脑为什么会蓝屏」= 0.147，换皮正例里最低的保住全文的是 0.161，0.16 正好落在缝里。
4. 基准新增 `全文相关` 指标。原来的「注入覆盖」把索引行里出现的 id 也算成功 ——
   门槛收紧时它看不出来（永远 100%），这也是之前没人发现门槛在漂的原因。
5. `stats.relevanceCoverage`：把本轮覆盖率塞进渲染诊断，出问题能一眼分清「没匹配上」和「匹配上但没过门」。

| 失败层 | 条数 | 说明 |
|---|---|---|
| **门（覆盖率不够）** | **14** | 其中 11 条排序层 rank=1 —— 排序早就选对了，是门不让进 |
| 排序层根本没分 | 3 | 词面完全不相交（如「快捷方式能不能改名」期望的是规则条目，但排序给的是别的） |
| 排序有、被复合分挤掉 | 2 | 相关层按重要度/新鲜度重排时把正确的挤出去了 |

结论：**门是主要瓶颈**。再看分布：正例覆盖率在 0.07–0.16 有一条长尾，而负例最高是 0.147（电脑蓝屏）——
两个分布**重叠**，说明单指标无论阈值定在哪都必然二选一。

### 改法：两票制（都要求 ≥ 2 个内容单元命中）

1. 主条件：覆盖率 ≥ 0.16（原规则，不动）
2. 放宽条件：**覆盖率 top1 == 排序层 top1**（两条不同口径的检索都指向同一条）+ 覆盖率 ≥ 0.07 + 命中 ≥ 2 个内容单元

判定抽成纯函数 `gateDecision()`，单测直接打规则。

### 为什么是「≥2 个单元」而不是「只要求一致」

实测（72 正例 / 35 负例，同一套评测集）：

| 规则 | 正例过门 | 负例误过 |
|---|---|---|
| 现状：覆盖率 ≥ 0.16 | 56/72 | 0/35 |
| 只要求「双信号一致」 | 64/72 | **1/35**（就是「电脑为什么会蓝屏」：cov 0.147、只命中「电脑」） |
| 双信号一致 **+ ≥2 单元** | **60/72** | **0/35** ← 采用 |
| 双信号一致 + 排序 top 自身覆盖率 ≥0.10 + ≥2 单元 | 61/72 | 0/35 |

最后一档只多 1 条，却要多算一遍每条记忆的覆盖率 —— 不值，没要。
也**主动放弃**了「64/72」那一档：多拿 4 条真命中、代价是放「电脑蓝屏」这类单字碰巧命中进来，不划算。

长句没动：那几条失败的 `agree=false`（覆盖率 top 与排序 top 不是同一条），两票制帮不上；

## v3.12 中文分词：从 bigram 换成「词」（2026-10-29）

起因是审查报告 A6：中文按 bigram 切时，文档里只要有两个字相邻就会被当成一个「单元」，
于是「基**本地**址」能拼出「本地」，把跟「本地部署」完全无关的记忆顶过门槛（真实库实测覆盖率 0.2375 > 0.16，
直接注入 1475 字符）。顺带 idf 也被污染：`地部`/`署要` 这种跨词碎片被当成词统计。

### 做法

1. **词典** `zh-words.txt`（跟插件一起版本化，一行一词，2–3 字，只收真词）：726 个唯一词（本节原写「715 条」是数错，实际文件 726；v3.14 扩到 754）。
   来源 = 82 条真实记忆 + 四套基准语料做无监督新词发现（频次 / 左右邻熵 / 内聚度），再逐条人工筛选。
2. **正向最大匹配** 切中文 run：命中词典词就整词成单元；**词典外片段退回 bigram 兜底**——
   未登录词（人名、新术语）还能靠字面命中，不会因为没进词典就彻底检索不到。
3. **3 字词额外保留词内 bigram**（验证门 → 验证门 + 验证 + 证门）：用户只问半截时还能对上。
   词内 bigram **不跨词边界**，所以 A6 那个「基本地址 → 本地」的拼接产物不会再出现。
4. **排序层与门槛层共用同一个** `segmentZhRun()`：v3.10 之前两者口径不同源，出现过「门槛过、排序层没候选」的错位。
5. `tokenize` / `contentUnitsOf` 结果按输入字符串缓存（上限 4000 条，满了整体清空）。

### 为什么不用 `Intl.Segmenter`（实测记录）

本机 Node v26.12.1 / ICU 78.3，`new Intl.Segmenter('zh',{granularity:'word'})`：

| 输入 | 输出 |
|---|---|
| 记忆插件的别名覆盖率怎么看 | 记忆 / **插 / 件** / 的 / 别名 / 覆盖 / **率** / 怎么 / 看 |
| 我把插件代码改完了，要不要重启 | 我把 / **插 / 件** / 代码 / 改 / 完了 / **重 / 启** |
| 本地部署要先看文档 | 本地 / 部署 / 要 / 先看 / **文 / 档** |
| 装完软件要不要登记台账 | 装 / 完 / 软件 / 要 / 不要 / 登记 / **台 / 账** |

常用词能切对，但「文档 / 插件 / 重启 / 覆盖率 / 台账」这类被拆成单字，单靠它会掉召回；
而且结果随 ICU 版本变，同一个测试换机器就不可复现。所以只把它当**候选词挖矿**的一次性工具，不进运行时。

### 阈值重标（这一步不能省）

分母变小了（一句话的单元数从「很多 bigram」变成「几个词」），覆盖率整体上移，旧阈值直接放负例进来。
用 74 正例 / 35 负例重标：

| 参数 | v3.11 | v3.12 | 依据 |
|---|---|---|---|
| `RELEVANCE_FLOOR` | 0.16 | **0.20** | 0.20 以下：短问法负例漏 3 条（电脑蓝屏 0.3296、MySQL 0.1918、快排 0.1428）；0.20 线上正例分数不丢 |
| `RELEVANCE_FLOOR_AGREE` | 0.07 | **0.12** | 词级口径下低覆盖率更少见，0.12 只放「两票一致」的真命中 |
| `EXPANSION_WEIGHT`（同义扩展权重） | 0.5 | **0.2** | 0.5 时「装完软件要不要登记」被同义扩展拉成 m74 第一（**零内容单元重合**却排第一）；0.2 同时修好换皮 recall@1 95.7% → 100% |
| 单单元护栏（短查询 ≤2 单元） | — | **0.40** | 单命中 + df≤1 且覆盖率 <0.40 不放：「电脑为什么会蓝屏」0.3296 挡住；「技能是怎么生成的」0.4379 放行 |

## v3.13 长句召回：拉丁子词 + 护栏改看「要注入的那条」（2026-10-29）

v3.12 把长句从 60% 拉到 66.7% 之后剩 5 条失败，逐条拆开是三类问题：

| 失败用例 | 真因 |
|---|---|

| 快捷方式能不能改名 / 文件放哪个盘 | **基准自己的 bug**：这两条的目标是 pinned 条目，长句基准没像短问法基准那样把 pinned 算命中 |

### 改法

1. **拉丁子词**：`latinSubUnits()` 把 `github.com`、`dsh-eval`、`chenqingsong-6017` 按 `. _ -` 拆段（只拆 ≥2 字符），排序层与门槛层都用。

2. **护栏改看排序 top 的证据**：`gateDecision` 新增 `rankEvidence`（要注入那条的命中单元数 / df），
   不再用覆盖率 top 的证据判——覆盖率 top 可能只是无关条目碰上一个词。
3. **相关层不再被 margin `break` 掐死**：循环里 margin 只 `continue`，覆盖率 top 还能走到；它同时豁免 margin（仍受 `MAX_RELEVANT` 与预算约束）。
4. **`RELEVANT_SHARE` 0.3 → 0.4**：两条全文经常装不下第二条（m71 的长文本先占满 450 字符额度）。
   小预算的回削也补上了「相关层」这一档：实测 `budget=600 / q=技能是怎么生成的` 会超 5 字符，现在会先削最后一条相关、落回索引行。
5. **长句基准补 pinned 判定**（与短问法基准一致），并删掉两条把 pinned 目标误报成失败的用例。

用 snap-research/locomo 的 10 个对话、1982 条可评分 QA 测**检索层**（只测 evidence 命中，不调模型）：

```powershell
node _selftest/memory-locomo.mjs --data <locomo10.json> [--compare]
```

`--compare` 会并排跑一条 30 行的朴素英文 BM25 做对照，用来分账：差距来自我们的打分，还是数据本身难。

### 改动 1：英文停用词（tokenize）

对照实验发现：英文检索比朴素 BM25 差 4.8 个点，差距全在 a/is/the/of 上 —— 中文侧早就有虚词规则，英文侧一直漏。

| LoCoMo 检索层 | 改前 | 改后 | 朴素 BM25 |
|---|---|---|---|
| recall@1 | 28.3% | **32.8%** | 33.1% |
| recall@5 | 51.1% | **55.7%** | 56.2% |
| MRR | 0.388 | **0.434** | 0.436 |

全停用词查询（"how are you"）退化为不过滤，避免什么都检索不到；URL / 路径子词不受影响。

### 改动 2：memory_search 补 `confidence` / `coverage`

原来只滤 `score > 0.0001`，问「MySQL 索引优化怎么做」也会吐 8 条 —— 有结果 ≠ 有答案（arXiv 2610.22668）。

现在返回体多两个字段：`confidence: 'ok' | 'low'`、`coverage`（0–1）。判定复用注入层同一个 `gateDecision`，但**不砍结果**（砍了会把「库里没有」误报成「有但不相关」），只在渲染时加一行提示。

真实库实测（90 条）：

| 查询 | coverage | confidence |
|---|---|---|
| cua 工具被过滤成几个（库里确实没有） | 0.179 | **low** |
| 今天上海天气怎么样 | 0.000 | low |
| 记忆检索 recall@3 是多少 | 0.356 | ok |
| 验证门 dsh-proof 收工前跑什么 | 0.805 | ok |

遗留：「MySQL 索引优化怎么做」coverage 0.251 仍过门（bench 里唯一失败项）。

## v3.16 记忆看得见：卡片导出（2026-10-30）

### 背景

调研了 GitHub 上「DSH 接 Obsidian」的现成方案（主要参考 [MengXinSu/dsh-viya-memory](https://github.com/MengXinSu/dsh-viya-memory)，MIT，143 tests，零依赖，声明兼容 `>=0.2.0-0 <0.3.0-0`）。

**结论是不换插件**：两套记忆会双重注入、工具重名，且现有 dsh-memory 有注入预算控制与三套检索基准，换掉等于丢掉这些。
只学它的核心长板——**记忆应该是人能看见、手改的文件**。

### 改动：`memory_export` + 卡片渲染

- 每条记忆渲染成 Obsidian 兼容的 `.md`（YAML frontmatter + 正文），任何 Markdown 编辑器都能开；
- frontmatter 字段：`id / kind / tag / tags / scope / pinned / importance / status / staleAfter / recheck / created / updated / usedCount / aliases`；
- 默认导出到 `<storeDir>/vault`（本机 `D:\AI\dsh-data\memory\vault`），**默认跳过已失效条目**，`includeArchived: true` 可一并导出；
- **JSON 仍是权威存储**：检索 / 注入预算 / 三套基准一律不动，导出是单向镜像，不参与排序与注入。

### 实测

### 没做的（诚实清单）

- **双链 `[[]]`**：89 条平铺记忆之间没有真实关系，硬造关系是假数据，不做；
- 自动导出（每次写入都镜像）：会放大写操作，先用工具手动触发。

## v3.17 写入覆盖：规则文件自动沉淀（2026-10-30）

### 起因

当天的自评结论：记忆系统第一位的问题不是检索，是**写入覆盖**。两个实测失败都属此类：

- 「cua 工具被过滤成几个」→ 库里根本没有；
- 「插件必须配什么测试」→ 躺在候选池 c3，没入库。

这两条规则只存在于 `AGENTS.md` / `.dsh/rules` 里 —— 而候选沉淀当时只抓用户消息，抓不到 agent 读到的规则。

### 改动

- 新增 `extractRuleCandidates(text)`：抽「硬规则行」（必须 / 一律 / 永远 / 禁止 / 不要 / 不得 / 务必 / 只能），
  跳过代码块、标题、表格、引用块，以及**以冒号结尾的引导句**（实测：「看资料时按这个顺序，不要一上来只搜 DSH 插件：」不是规则）；
- 新增 `collectRuleFiles(cwd)`：工作区 `AGENTS.md` / `CLAUDE.md`、`.dsh/rules/*.md`、全局 `~/.dsh/AGENTS.md`；
- `agent/turn-stopping` 里追加规则沉淀，**只进候选池、不自动入库**（影子模式不变，仍要人点头）。

### 实测

| 项 | 结果 |
|---|---|
| 本工作区 4 个规则文件 | 抽出 **15 条**硬规则行 |
| 单测 | **109 项通过**（+1：只抽硬规则 / 跳过代码块表格 / 去重）|
| 三道门 `npm run check` | 通过 |

### 已知边界（诚实）

- **无 cwd 的会话不扫**：否则测试环境会被全局 `AGENTS.md` 污染（实测踩过，旧测试 pending 1→2 失败）；
- 每回合最多 `MAX_CANDIDATES_PER_TURN`（2）条，渐进进池，不会一次灌爆；
- 抽出来的是「行」不是「句」，有些是半句（如「后者只能靠真实调用发现」），末尾以冒号/破折号收尾的已过滤，但仍有噪声 —— 候选池本来就是给人筛的。

## v3.18 自动入库 + 预算保护（2026-10-30）

### 思路来源

arXiv [2610.27377](https://arxiv.org/abs/2610.27377) *REM: What to Store, When to Recall, What to Forget in Experience Memory for Coding Agents* ——
写入策略要在「该记」和「该忘」之间做**预算权衡**，而不是一律推给人审。
配套参考 Letta 的记忆块自动编辑（sleep-time）与 hindsight 的 consolidation 讨论（源码/博客层级，非论文）。

### 改动

v3.17 把规则抽进候选池，但**候选池要人审，等于写入还是半自动**。v3.18 加一条高置信度通道：

- **规则文件来的硬规则**（来源=规则文件 + `kind: rule` + 与现有记忆相似度 < 0.7）→ **直接入库**，标记 `status: draft`（未证实，可用 `memory_update verified:true` 复核）；
- 用户消息来的候选 → 仍进候选池等人审（措辞模糊、上下文不明，不该自动吃）；
- **预算保护**：入库前若超 `maxBytes`，先归档「最低价值」条目——`usedCount=0` + 非 pinned + 非 rule + 非 draft 中 `effectiveImportance` 最低者；
- **归档是可逆的**：写 `status: deprecated` + `archivedAt` + `archiveReason`，**不物理删除**，`memory_search` 仍能搜到，`memory_update` 可恢复。

### 为什么不是「超预算就拒绝写入」

v1.1 的刻意取舍是「拒绝写入，不自动淘汰」。自动入库必须自己腾地方，否则一条都进不来（当前存储 **7837 / 8000**，只剩 163 字符）。
折中是：**归档替代删除**——不丢信息、可逆、可审计，且归档后不再占注入预算。

### 实测

| 项 | 结果 |
|---|---|
| 单测 | **110 项通过**（+1：deprecated 不注入、draft 参与注入）|
| 三道门 `npm run check` | 通过 |
| 当前存储水位 | 7837 / 8000（首次自动入库必然触发一次归档，属预期行为）|

### 风险与边界（诚实）

- ~~自动入库没有独立单测~~ → **v3.19 已补集成测试**（`memory.test.mjs` 真跑 `agent/turn-stopping`：临时工作区放 AGENTS.md → 触发钩子 → 断言规则以 `draft` 入库、且预算不足时确有条目被归档）；仍待真实环境验证的是「多回合累积后的归档选择是否合理」；
- 归档判据是「`usedCount=0` 且非 pinned」——刚写进去还没被引用过的条目也可能被归档，**这是刻意选择**（新 = 未验证），但如果你在意某条，钉 `pinned: true` 即可豁免；
- 每回合最多自动入库 2 条（沿用 `MAX_CANDIDATES_PER_TURN`），不会一次灌满；
- `draft` 条目在注入时带 `❓` 标记（trustMark），提醒模型这是未复核的。

## v3.19 时效降权（2026-10-30）

依据 arXiv [2610.36308](https://arxiv.org/abs/2610.36308)：过时的版本是记忆检索的主要错误源——
证据预算从 64 涨到 512 token，准确率反而从 45% 掉到 32%，原因是旧版本在干扰。

### 改动

- `scoreEntries` 对 `staleAfter` 已过的条目乘 `STALE_PENALTY = 0.55`——**只降权不过滤**，过期信息仍可检索（不丢信息），但不该排在前面；
- `memory_search` 返回体新增 `stale: true`，调度方能直接判读；
- 新增导出 `isStaleEntry(entry, today)`。

### 验证（三套基准零回归）

| 基准 | 结果 |
|---|---|
| 中文 bench | recall@1 **97.1%** / @3 **100%** / 负例误注入 4.8%（不变）|
| LoCoMo | recall@1 **32.8%** / @5 55.7% / MRR 0.434（不变）|
| 单测 | **111 项通过**（+1：过期判据 + 同文本时未过期排前）|
| 三道门 | 通过 |

## v3.20 归档分文件冷存（2026-10-30）

起因是真实库的一次体检：93 条里 48 条是归档（被取代/被预算保护挤掉），**既不计预算、也不参与注入，却永远躺在 memory.json 里**，
每次 `memory_list` 把它们一起吐出来（实测 37,449 字节）。取经 mem0 / MemOS / memobase / Letta / Graphiti 五家（源码级）后定的做法：
**软失效保留、但归档搬出主库**，而不是物理删（五家里只有 memobase / Letta 的覆盖式会丢历史，它们恰恰是简化实现）。

### 改动

- **主库只存生效条目**：`memory.json` 只写非归档条目；归档条目写 `archive.json`（与 `aliases.json` 同级的旁路文件，`{version:1, entries:[]}`）。
- **写序安全**：persist 先原子写 archive.json、再写 memory.json——归档写失败就整体失败，不会出现「主库摘掉了、归档没落地」的丢数据窗口。
- **加载合并**：`loadArchive()` 把归档读回内存态（主库同 id 优先，归档只补缺），所以检索/审计/导出对归档的可见性与 v3.19 一致；
  归档文件损坏时返回空、不抛错，**不连累主库启动**（fail-safe）。
- **`memory_list` 默认不返回归档**，新增 `includeArchived` 参数（默认 false）；返回体新增 `active` / `includeArchived` 字段，表头改成「N 条生效 / M 条归档」并提示怎么看归档。
- **新工具 `memory_restore`**：被预算保护挤掉的条目（deprecated 且未被取代）可以恢复成生效记忆；被 `supersededBy` 取代的不许直接恢复（否则会出现两个版本），提示用 `memory_add` 重写。恢复会先查预算，超了拒绝。
- 新增导出 `isArchivedEntry(entry)`，把「归档判定」收成一处（原来 `activeEntries` 内联，两处口径容易漂移）。

### 验证

| 项 | 结果 |
|---|---|
| 单测 | **117 项通过**（新增 5 项 v3.20 用例：默认不列归档 / 分文件落盘 / 重载归档不丢 / restore 拒绝被取代条目 / 归档损坏 fail-safe）|
| 真实库副本冒烟 | 48 条存量 → 47 生效 + 1 归档，`memory_list` 只列 47，**未产生任何写入**（主库仍 48 条、archive.json 未创建）|
| 中文 bench | recall@1 100% / @3 100% / 负例误注入 9.5%（与改动前一致）|
| 卫生检查 | 硬规则 6/6 注入、注入 1469 字符（上限 1750）、失效未漏注入 ✅ |
| 三道门 | 通过（18 个测试全量）|

### 兼容与迁移

- **旧版本插件读新库没问题**（memory.json 依旧是合法库，只是少了归档条目）；旧版本若把归档写回主库，新版本加载时再拆出来，自愈。
- 存量归档**懒迁移**：新版本第一次写库（任意 memory_* 写操作）时才会把归档搬进 archive.json；不写就一直留在主库，但 `memory_list` 已经默认不列它们。
- 回滚：archive.json 是纯旁路文件，删掉它只是丢归档历史，主库不受影响；把归档并回主库 = `memory_restore`（仅未取代的）。
